## Outcome

### Original coordinator (unchanged)

- Forced two-stage approval race yields an `ALLOW` resolution with inconsistent entry-chain linkage; execution validation fails closed with `chain_tampered`.
- Two independent processes against one research-authored SQLite store reproduced this in 3/3 controlled trials.
- Abrupt process termination after a standalone entry write left a partial committed record in the research store.

### Candidate migration patch (temporary checkout, not applied upstream)

- Adds a **separate optional** `AtomicApprovalStore` structural protocol without changing the original eight-method `ApprovalStore` interface.
- Adds a `approval_transaction(request_id)` context to the built-in `InMemoryApprovalStore`, using its existing reentrant lock. This protects only workers sharing one Python-process store.
- Wraps `ApprovalCoordinator.submit_entry()` in a store-provided transaction when available.
- Adds a backward-compatible `require_atomic_submission=False` coordinator option; in legacy mode, a custom store without transactions continues to run but emits an explicit runtime warning. This **does not eliminate the race for a legacy nontransactional store**.
- With `require_atomic_submission=True`, a missing transaction implementation raises an explicit protocol error **before any vote is written**. The high-level `govern()` wrapper denies execution when the protocol bridge encounters that error.
- Our disposable SQLite store implements `approval_transaction()` with `BEGIN IMMEDIATE`. The patched coordinator validates both votes and preserves the hash chain in 3/3 separately spawned, two-process trials.
- Under an actual `os._exit(87)` after entry append but before resolution, SQLite rolled back the incomplete vote; the later retry completed with one record, not two.

## High-level govern() results

The full implementation of Microsoft's **existing** `agentmesh.governance.govern.govern()` function was imported from the pinned source. No copy or reimplementation of `govern()` was used.

- One approved, policy-gated fake SQLite write succeeded and recorded an audit receipt with the action digest and approval request ID.
- Wrong-identity and negative approvals denied execution and wrote nothing.
- Strict mode against an unmodified legacy backend denied before effect.
- Legacy compatibility mode remained usable but logged an explicit non-atomic backend warning.
- A two-required-stage approval with only one synchronous approval vote denied safely; `govern()` does not by itself wait for later approval stages to arrive.
- Two distinct approved writes produced distinct protocol request IDs and corresponding audit entries.

The test-only source bootstrap intentionally bypassed broader package initializers. `pydantic`, `PyYAML`, and `pytest` were installed in CI, and the wrapper plus its actual source dependencies executed. **The consolidated distribution and its full sidecar/runtime integrations have still not been installed or exercised.**

## API migration decision and limitations

This proposal preserves source compatibility for custom stores and provides a strict opt-in for deployments needing atomicity. It **deliberately keeps the old nontransactional behavior in compatibility mode**; doing so avoids breaking third-party stores but cannot provide the full guarantee to these users. Whether the safe default should be strict, and how to schedule migration, belongs to upstream maintainers.

A production adapter must implement a transaction spanning entry reads, entry insertion, resolution writes and status transitions. A shared local `threading.RLock` is insufficient across separate processes and machines. The research SQLite implementation uses a coarse `BEGIN IMMEDIATE` write lock and is **not presented as a production or Microsoft-supplied backend**.

Required upstream-readiness checks:

1. Decide strict-default versus migration-warnings policy with maintainers, and confirm whether the existing public contract promises concurrent submissions.
2. Validate with an actual supported production data store, full installed package, and real approval transport where appropriate.
3. Evaluate double-vote, conflicting votes, expiry, cancellation, crash/recovery, and per-request lock granularity with database-engine semantics.
4. Add direct protocol regression tests inside upstream's native test layout and review compatibility of the decorator, exception types, and store capability detection.
5. Confirm novelty, triage severity, and responsible reporting route. The upstream `SECURITY.md` says potential vulnerabilities must be privately reported, not filed as public issues.
6. **Obtain user approval before external maintainer contact, security disclosure, opening a PR, or publishing a claim about a vulnerability.**

The user's repository `main` and the Microsoft's repository are unchanged.
